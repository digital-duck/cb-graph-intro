Concept Book: As Topology

Graph Intro Ch07 · Generated by SPL

收获

as_topology 是整本书的终点:它回答了一个贯穿全书的问题——一个由多个步骤、多个模型和多个子工作流组成的程序,其"形状"究竟是什么? 在前面的章节中,我们分别学习了单次生成、CALL 子工作流组合、CALL PARALLEL 并发分支、EVALUATE 语义分支和 WHILE 迭代精炼。as_topology 把这些零散的构件统一为一张图:节点是计算单元(确定性工具或概率性 LLM 调用),边是数据依赖。

定义

在这里,拓扑(topology)指的是工作流中各节点之间连接关系的结构,而不是每个节点内部的具体内容。两个工作流如果节点间的依赖方式相同,即使提示词和模型完全不同,也拥有同一种拓扑。这正是 DODA(Design Once, Deploy Anywhere)的结构基础:.spl 文件固定了逻辑拓扑,而 --adapter 与 --model 只改变物理执行。

工作示例

考虑自我精炼(self-refine)工作流:

  • GENERATE 产生草稿 @draft;
  • EVALUATE 评审草稿;
  • 若未达标,WHILE 回到修改步骤。

    • 其拓扑是一条带回边的链:草稿 → 评审 → 修改 → 评审。若把评审拆成三个独立视角并用 CALL PARALLEL 分发,拓扑变成"扇出—扇入"结构:一个节点分叉为三条并行分支,再汇合为一个节点。仅凭拓扑,不必运行任何模型,就能读出:关键路径长度、可并行宽度、是否存在循环。

    解决问题

    拓扑让我们能够在运行之前推理程序。例如:

  • 延迟估计:总耗时约等于关键路径上各节点耗时之和,而不是所有节点之和;并行宽度为 $w$ 时,理想加速比上限为 $w$。
  • 调度:在 Momagrid 上,同一层的独立分支可路由到不同节点。
  • 转译:spl3 splc 把同一拓扑生成为 LangGraph、Go 或 TypeScript 代码,因为目标框架只需保持图结构一致。
  • 验证:检测悬空变量、不可达节点和无退出条件的循环。

    • 与各应用领域的联系

    本节所对应的概念没有列出具体的应用领域,因此这里只说明它通用的落脚点:凡是需要设计一次、多处运行的场景——跨框架迁移、分布式推理调度、工作流的可视化审查——都从拓扑这一层抽象获益。无论目标是课堂上的单机 Ollama,还是校园里由学生搭建的 Momagrid 网格,拓扑都保持不变。

    邀请

    选择你最熟悉的一个食谱(例如 cookbook/005_self_refine),先只画出它的拓扑图,标出关键路径与并行宽度,再用 spl3 splc --target langgraph 编译并对照结果。这个练习会让你真正体会到:理解结构,就是掌握了在任何地方重新部署它的能力。
