Big O Notation

When you write an algorithm, two questions matter immediately: does it produce the right answer, and how fast does it run as the input grows? Big O notation is the standard language for answering the second question. It describes the growth rate of an algorithm's runtime (or memory use) as a function of input size $n$, ignoring constant factors and lower-order terms that become irrelevant at scale.

Formally, we say $f(n) = O(g(n))$ if there exist constants $c > 0$ and $n_0$ such that $f(n) \leq c \cdot g(n)$ for all $n \geq n_0$. In practice, this means: find the dominant term in your operation count, drop the coefficient, and that's your Big O class.

Common classes, slowest to fastest growth:

| Notation | Name | Example | |---|---|---| | $O(1)$ | Constant | Array index lookup | | $O(\log n)$ | Logarithmic | Binary search | | $O(n)$ | Linear | Single loop over a list | | $O(n \log n)$ | Linearithmic | Merge sort | | $O(n^2)$ | Quadratic | Nested loops | | $O(2^n)$ | Exponential | Naive subset enumeration |

Worked example. Consider two functions that check whether a list contains any duplicate values:

def has_duplicate_slow(lst):          # O(n^2)
    for i in range(len(lst)):
        for j in range(i + 1, len(lst)):
            if lst[i] == lst[j]:
                return True
    return False

def has_duplicate_fast(lst):          # O(n)
    seen = set()
    for x in lst:
        if x in seen:
            return True
        seen.add(x)
    return False

The first version compares every pair — roughly $n^2/2$ comparisons — so it is $O(n^2)$. The second scans the list once, trading memory for speed, making it $O(n)$. At $n = 10{,}000$, that difference is roughly 50 million operations versus 10,000.

Problem-solving application. When optimizing code, locate the innermost loop or the operation that executes most frequently, express its count as a polynomial in $n$, and keep only the highest-degree term. If you see a loop inside a loop, suspect $O(n^2)$ and ask whether a hash set or sort could eliminate one dimension. Sorting costs $O(n \log n)$ but often enables $O(\log n)$ lookups afterward — a classic trade that converts an $O(n^2)$ search into $O(n \log n)$ overall. Practice by estimating Big O before benchmarking; if your estimate and your profiler disagree, that gap reveals a hidden algorithmic cost worth investigating.
